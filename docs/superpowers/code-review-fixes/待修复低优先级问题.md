## Task 3: 终端 Tab 懒加载

**审查编号:** #21
**严重程度:** 中（性能）
**涉及文件:** `src/components/TerminalPanel.tsx`, `src/components/TerminalInstance.tsx`

**问题:** 所有终端 Tab（包括不可见的）都保持挂载，每个都创建完整的 xterm Terminal 实例。20+ 终端时内存和 CPU 消耗显著。

**修复步骤:**

- [ ] **Step 1: 在 TerminalInstance 中添加 disposed 状态**

不活跃的 Tab 卸载 xterm 实例，只保留一个占位 DOM 节点。

- [ ] **Step 2: 切换回 Tab 时重建 xterm**

使用后端已有的 `peek_terminal_output` 获取历史输出，重建 xterm 并回放。

- [ ] **Step 3: PTY output 缓冲设计**

在 TerminalInstance 中维护最近 N 条输出的环形缓冲区，切换 Tab 时用于恢复显示。

- [ ] **Step 4: 在 TerminalPanel 中控制渲染**

```tsx
// 只渲染当前 Tab + 前后各 1 个 Tab 的 xterm 实例
const visibleRange = useMemo(() => {
  const idx = sessions.findIndex(s => s.id === activeSessionId);
  return new Set(sessions.slice(Math.max(0, idx - 1), idx + 2).map(s => s.id));
}, [sessions, activeSessionId]);
```

- [ ] **Step 5: 验证**

手动测试：打开 20+ 终端 Tab，切换观察内存变化。

## Task 6: SSH 文件传输异步化

**审查编号:** #26
**严重程度:** 中
**涉及文件:** `src-tauri/src/services/ssh_session_service.rs`

**问题:** `upload()` 和 `download()` 在持有 per-session Mutex 的同时执行同步文件 I/O。大文件传输期间，同一 SSH session 的其他操作被阻塞。

**修复步骤:**

- [ ] **Step 1: 提取 SFTP handle 到锁外**

```rust
pub fn upload(&self, terminal_id: &str, remote: &str, local: &str) -> Result<(), String> {
    let sftp = {
        let sessions = self.sessions.lock().map_err(|e| e.to_string())?;
        let session_arc = sessions.get(terminal_id).ok_or("Session not found")?;
        let session = session_arc.lock().map_err(|e| e.to_string())?;
        // clone SFTP handle（如果 ssh2 crate 支持）
        session.sftp.clone().ok_or("SFTP not available")?
    }; // 锁在此释放
    // 在锁外执行文件传输
    sftp.upload(remote, local)?;
    Ok(())
}
```

- [ ] **Step 2: 如果 SFTP 无法 clone，改用独立 SFTP session**

```rust
// 为传输操作创建独立的 SFTP session
let传输_sftp = ssh2::Session::new()?.sftp()?;
```

- [ ] **Step 3: 大文件传输添加进度回调**

```rust
pub fn upload_with_progress(
    &self,
    terminal_id: &str,
    remote: &str,
    local: &str,
    on_progress: impl Fn(u64, u64),
) -> Result<(), String> { ... }
```


## Task 8: lock().unwrap() 全面改造 ✅

**审查编号:** #29
**严重程度:** 低
**涉及文件:** `terminal.rs`, `web_service.rs`, `ws.rs`

**问题:** 大量 `lock().unwrap()` 在 mutex poisoned 时会导致 panic 级联。

**已完成修复:**
- 3 个文件共 24 处 `lock().unwrap()` 全部替换为 `lock().unwrap_or_else(|e| e.into_inner())`
- `close_terminal` / `close_terminal_with_check` 重构：`child.kill()` + `child.wait()` 移到锁外，消除锁持有期间阻塞的风险
